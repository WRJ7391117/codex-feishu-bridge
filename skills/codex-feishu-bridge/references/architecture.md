# Architecture

The bridge has five independent layers:

1. Feishu app: Bot permissions, events, callbacks, and the custom menu.
2. bundled lark-cli: one bot profile and three long-running event consumers.
3. `bridge.py`: user/chat allowlist, project authorization, task catalog, per-user state, deduplication, and replies.
4. Codex Desktop: local task catalog, authoritative paginated/JSONL history, and the official shared local app-server; legacy IPC remains supported.
5. macOS runtime: menu bar App and user LaunchAgent.

Event flow:

```text
Feishu -> lark-cli event consume -> bridge.py -> optional attachment download -> shared Codex app-server
Feishu <- lark-cli card patch + text/image reply <- bridge.py <- Codex task state/result

```

The bridge consumes:

- `im.message.receive_v1` for text, image, file, and audio input
- `card.action.trigger` for project/Task selection, Task creation/archive confirmation, stop, and one-time approval decisions
- `application.bot.menu_v6` for the “Task 管理” submenus “当前 Task”, “切换 Task”, “新建 Task”, and “归档当前 Task”; the “桌面task” submenus “订阅桌面 Task”, “接续当前 Task”, and “接续其他 Task”; and the “模型设置” submenus “修改当前 Task 模型”, “压缩当前 Task 上下文”, and “Codex 额度用量”

Card actions differ from ordinary events at the WebSocket ingress. The bundled CLI registers `card.action.trigger` with `OnP2CardActionTrigger`, forwards the unchanged raw event into the local bus, and immediately returns a valid `CardActionTriggerResponse` with a visible processing toast. This synchronous response prevents Feishu error `108002`; the later complete-card update remains a separate delayed-update API call.

Selection is stored by permitted Feishu user, not by individual incoming message. It persists across ordinary turns and progress updates, but a completed, failed, or stopped Task becomes current immediately before its final text reply so the user's next message naturally follows the latest result. Terminal-result selection and text delivery are serialized per user; when parallel Tasks finish, the last delivered result wins. Favorites, recent-use order, and the latest question/answer summary are also isolated by user. Each user has one logically current status card; it is patched in place when possible and shows the latest exchange, while an unpatchable old Feishu message may remain in history and the new card becomes the only card tracked for future updates. The “当前 Task” submenu sends the latest status card to the bottom of the chat and makes it the tracked card; only a user with no valid current Task is routed to selection. Account quota is kept out of Task cards; the separate “Codex 额度用量” menu returns the same Mac account's compact refreshable quota card to every bridge-allowlisted user. Run, queue, approval, and result cards retain their owning Task and change from “当前 Task” to an accurate role label after a switch. The “切换 Task” card persists its Project context and revision. When a current Task exists it also offers “取消切换”, which preserves the selected Task and message route; inside Desktop handoff it returns to that Task's handoff confirmation. A Task callback from a replaced Project list cannot change selection; the bridge refreshes that same card to the latest Project and asks the user to choose again. Repeated pending intents for the same non-destructive selector or view control coalesce to the newest tap. The primary selection card updates before run, approval, queue, and current-status identity cards, whose refreshes are coalesced by user in a lifecycle-bound background worker. Creation and archive use separate Bot menu entries and dedicated cards. Archive requires a second confirmation and revalidates the current Task before changing state. Archive and restore show a processing state while their Desktop calls run outside the global state lock. A subscribed Task's new terminal turn sends a result card followed by the complete text split into ordered idempotent replies; failed chunks, images, audio, and files use the durable reply queue and never rerun Codex. `state.json` also stores recent message IDs, bridge turn IDs, access requests, Task search/page state, pending Task inputs, failed final replies/images/audio/files, and undelivered queue/progress card updates. Its file mode is restricted to the current macOS user.

The “桌面task”→“接续当前 Task” menu resolves only the requesting user's bridge-selected current Task. It reads the newest turn from the authoritative backend and shows the exact project, Task title, and Desktop state before confirmation. The callback revalidates the current Task; without one it opens selection and never guesses by recency. A completed turn returns immediately. A running turn creates a durable per-user Task/turn/message subscription. The shared observer includes these handoff-only Tasks, and one terminal event reconciles every waiting user. A bridge-owned turn keeps its normal delivery as the sole reply to its originating user. Menu-card delivery failures retain the original idempotency key and callback context.

The “桌面task”→“订阅桌面 Task” menu stores up to twenty authorized Task IDs per Feishu user. Each entry starts at the current authoritative history cursor, so old results are not backfilled. A persistent shared event connection resumes authorized targets and reconciles terminal events and reconnect gaps. State-file hooks update targets; normal shared operation does not periodically scan Task storage. Legacy Desktop and disconnected recovery retain bounded compatibility scans. Paginated Tasks use database history even when stale JSONL remains, and existing subscription cursors migrate with the backend. Delivery uses deterministic idempotency keys and durable attachment retries. Access is revalidated, bridge ownership is read at delivery time, and only the originating user's extra subscription reply is skipped. A delivered result becomes current for follow-up.

Each allowlisted user has `allowed_projects`. `*` grants all projects; otherwise names match Codex Desktop sidebar project names exactly. Task access is checked when building the list and again immediately before selection or submission. Removing project access therefore invalidates a previously selected Task. Text, card, and Bot-menu events use their own `sender_id` or `operator_id`, so users do not share selection state.

Text, image, file, and audio messages share the same authorization, selection, and deduplication path. Attachments are downloaded from resource keys belonging to that exact Feishu message into a per-turn temporary directory, checked for directory containment, size, and supported type, and deleted after the turn. The defaults are four images at 20 MB each and four files at 50 MB each; archives and executables are not accepted.

Events are serialized per Feishu user so one user's taps keep their original order while another user's slow API call does not block them. Maintenance and durable-delivery retries run outside the ingress loop. Each accepted turn runs in a background worker, and a run registry enforces one active turn per Task with a configurable global limit, defaulting to two concurrent Tasks; project membership does not serialize otherwise independent Tasks. Later inputs enter a bounded persistent FIFO queue, retain their original Feishu reply target and attachment resource references, and start automatically when both limits allow. Their cards state whether the cause is same-Task serialization, global capacity, or an already-running Desktop turn, show the position within that Task's queue, and allow cancellation. The first status reply is a Card 2.0 message; later phases patch that same message once with a short foreground timeout. If Feishu remains unreachable, the bridge persists the missing queue card or latest patch and retries it in the background without rerunning Codex. Patches for the same message are coalesced to the newest card, and an undelivered queue card is discarded once that queued input has started. A stop callback sets the local cancellation flag and, for Desktop runs, sends `thread-follower-interrupt-turn`. The bridge reports a run as stopped only after local CLI termination or Desktop confirmation.

The bridge reads `account/rateLimits/read` from the local Codex app-server once per minute and writes the normalized account-level limit buckets alongside aggregate health values in private `runtime-status.json`: active consumers, active runs, configured limit, and last Feishu event time. The Mac App combines that file with queue counts from private state and refreshes its visible dashboard every two seconds. No user, Chat, project, or Task identifier is written to the aggregate health file. Feishu's second-level Task usage analysis reads structured Token and event counters from only the local rollouts the requesting user is authorized to see. It ranks Tasks for the local day or current main-quota reset period and explains cached-context, model-call, reasoning, tool, and compaction drivers. Results are cached in process memory for five minutes and are explicitly presented as relative Task diagnostics rather than exact per-Task billing or quota deductions.

Current Desktop and Bridge must share the managed local daemon. Bridge uses the public CLI proxy as a raw transport, performs the WebSocket-over-Unix upgrade, and keeps RPC responses, notifications, and server requests separate. On upgrade, Desktop needs one safe restart to adopt its supported shared-daemon setting. The protected App Tools pipe is not used. Legacy IPC still follows the owner window when available.

Desktop state snapshots can expose command, file-change, and permission requests. The bridge creates a separate approval card and forwards only an explicit one-time allow or deny response. It never grants a session-wide or permanent permission from Feishu.

The submission path keeps the original Task ID and inherits its directory, model, effort, speed, approval policy, and permissions. A missing or unlistened legacy IPC endpoint selects the public app-server automatically. A definite legacy `no-client-found` retains one supported deep-link activation and explicit manual choices. Desktop-bundled CLI version compatibility is checked before resume. Inputs use `localImage`, `localAudio`, and file `mention` items. A unique client message ID is durably journaled before `turn/start`; a possibly submitted request is never replayed or switched to another backend. An uncertain journal blocks only that Task's later inputs. Shared events or paginated `thread/turns/list` history match the client ID to the real turn and recover delivery, including completion during disconnection. One-time approvals, settings, compaction, and interruption use the same live connection, without an opaque `codex exec resume` subprocess.

For results, the bridge sends text first and images/audio/files afterward. It recognizes local or remote Markdown image references in the final message and also collects `image_generation_end.saved_path` events written during the current rollout segment. Text-linked local resources must resolve inside the selected Task working directory or the dedicated private `result-attachments` directory; this prevents a prompt from turning an arbitrary Mac path into a Feishu upload. Current-turn image-generation events are trusted separately and scoped by the rollout byte offset recorded immediately before starting the only active turn because they do not contain a turn ID. Local audio explicitly linked with either ordinary Markdown or Codex Desktop's `![audio](path)` form is separated before image parsing: files whose Ogg container contains `OpusHead` use a native Feishu voice message, while AAC, FLAC, M4A, MP3, WAV, and non-Opus Ogg use an attachment. Other supported local files explicitly linked by the final result are returned as attachments; ordinary web links are left unchanged. Local resources are uploaded from their parent directory because lark-cli requires relative paths. A local image, audio, or result file that cannot reach Feishu is copied to a private bounded spool, retried with its original type and idempotency key, and deleted only after confirmed delivery. The defaults are eight images, four audio items, and four result files per turn, with a 50 MB limit for each audio or result file.

Task creation, naming, search, and archive use the published Codex app-server JSON-RPC protocol. The bridge still reads the Desktop catalog for the sidebar-facing project and Task list. Pinning is deliberately not implemented because the current app-server schema has no supported pin method; the bridge never writes Codex SQLite or Electron state directly.
