# Architecture

The bridge has five independent layers:

1. Feishu app: Bot permissions, events, callbacks, and the custom menu.
2. bundled lark-cli: one bot profile and three long-running event consumers.
3. `bridge.py`: user/chat allowlist, project authorization, task catalog, per-user state, deduplication, and replies.
4. Codex Desktop: local task catalog, task rollout files, and desktop IPC.
5. macOS runtime: menu bar App and user LaunchAgent.

Event flow:

```text
Feishu -> lark-cli event consume -> bridge.py -> optional attachment download -> Codex Desktop IPC
Feishu <- lark-cli card patch + text/image reply <- bridge.py <- Codex task state/result

```

The bridge consumes:

- `im.message.receive_v1` for text, image, file, and audio input
- `card.action.trigger` for project/Task selection, Task creation/archive confirmation, stop, and one-time approval decisions
- `application.bot.menu_v6` for the “Task 管理” submenus “当前 Task”, “切换 Task”, “新建 Task”, and “归档当前 Task”; the “管理桌面 Task” submenus “订阅桌面 Task”, “接续当前 Task”, and “接续其他 Task”; and the top-level “Codex 额度用量” menu

Card actions differ from ordinary events at the WebSocket ingress. The bundled CLI registers `card.action.trigger` with `OnP2CardActionTrigger`, forwards the unchanged raw event into the local bus, and immediately returns a valid `CardActionTriggerResponse` with a visible processing toast. This synchronous response prevents Feishu error `108002`; the later complete-card update remains a separate delayed-update API call.

Selection is stored by permitted Feishu user, not by individual incoming message. It persists across ordinary turns and progress updates, but a completed, failed, or stopped Task becomes current immediately before its final text reply so the user's next message naturally follows the latest result. Terminal-result selection and text delivery are serialized per user; when parallel Tasks finish, the last delivered result wins. Favorites, recent-use order, and the latest question/answer summary are also isolated by user. Each user has one logically current status card; it is patched in place when possible and shows the latest exchange, while an unpatchable old Feishu message may remain in history and the new card becomes the only card tracked for future updates. The “当前 Task” submenu sends the latest status card to the bottom of the chat and makes it the tracked card; only a user with no valid current Task is routed to selection. Account quota is kept out of Task cards; the separate “Codex 额度用量” menu returns the same Mac account's compact refreshable quota card to every bridge-allowlisted user. Run, queue, approval, and result cards retain their owning Task and change from “当前 Task” to an accurate role label after a switch. The “切换 Task” card persists its Project context and revision. When a current Task exists it also offers “取消切换”, which preserves the selected Task and message route; inside Desktop handoff it returns to that Task's handoff confirmation. A Task callback from a replaced Project list cannot change selection; the bridge refreshes that same card to the latest Project and asks the user to choose again. Repeated pending intents for the same non-destructive selector or view control coalesce to the newest tap. The primary selection card updates before run, approval, queue, and current-status identity cards, whose refreshes are coalesced by user in a lifecycle-bound background worker. Creation and archive use separate Bot menu entries and dedicated cards. Archive requires a second confirmation and revalidates the current Task before changing state. Archive and restore show a processing state while their Desktop calls run outside the global state lock. A subscribed Task's new terminal turn sends a result card followed by the complete text split into ordered idempotent replies; failed chunks, images, and files use the durable reply queue and never rerun Codex. `state.json` also stores recent message IDs, bridge turn IDs, access requests, Task search/page state, pending Task inputs, failed final replies/images/files, and undelivered queue/progress card updates. Its file mode is restricted to the current macOS user.

The “管理桌面 Task”→“接续当前 Task” menu resolves only the requesting user's bridge-selected current Task. It reads the newest complete turn backward from the end of the rollout, so opening the confirmation card does not become slower as Task history grows. It shows that exact project, Task title, and latest Desktop state before any handoff; the user must confirm, select another Task, or cancel. The confirmation callback revalidates that the card's Task still equals the user's current Task, preventing stale cards from subscribing to another conversation. With no valid current Task, the bridge opens the Task selector and never guesses from running or recent Tasks. A completed turn is returned immediately after confirmation. A running turn creates a durable per-user subscription containing only the fixed Task/turn/message route and rollout cursor; the background loop reads only newly appended rollout records and pushes the terminal result after completion. If the same user already owns a bridge-started run, its normal delivery remains the sole final reply instead of creating a duplicate subscription. New Bot-menu cards use a bounded foreground send; a timeout is durably retried with the same idempotency key and restores the card context after delivery.

The “管理桌面 Task”→“订阅桌面 Task” menu stores up to twenty authorized Task IDs per Feishu user. Each entry starts at the rollout's current complete-record offset, so old results are never backfilled. The background poller reads only appended complete JSONL records, persists the cursor and active turn across restarts, and sends each new terminal result with a deterministic idempotency key before advancing the cursor. A failed Feishu send therefore retries the same delivery instead of losing or duplicating it. Revoked project access, a removed allowlist user, or an archived Task removes the affected subscription. A bridge-owned turn skips the extra subscription push only for its originating user; other subscribers still receive it. Result images and explicitly linked files reuse the durable attachment spool. Selecting a subscription does not change the user's current Task, while a delivered result follows the existing latest-result behavior and becomes current for immediate follow-up.

Each allowlisted user has `allowed_projects`. `*` grants all projects; otherwise names match Codex Desktop sidebar project names exactly. Task access is checked when building the list and again immediately before selection or submission. Removing project access therefore invalidates a previously selected Task. Text, card, and Bot-menu events use their own `sender_id` or `operator_id`, so users do not share selection state.

Text, image, file, and audio messages share the same authorization, selection, and deduplication path. Attachments are downloaded from resource keys belonging to that exact Feishu message into a per-turn temporary directory, checked for directory containment, size, and supported type, and deleted after the turn. The defaults are four images at 20 MB each and four files at 50 MB each; archives and executables are not accepted.

Events are serialized per Feishu user so one user's taps keep their original order while another user's slow API call does not block them. Maintenance and durable-delivery retries run outside the ingress loop. Each accepted turn runs in a background worker, and a run registry enforces one active turn per Task with a configurable global limit, defaulting to two concurrent Tasks; project membership does not serialize otherwise independent Tasks. Later inputs enter a bounded persistent FIFO queue, retain their original Feishu reply target and attachment resource references, and start automatically when both limits allow. Their cards state whether the cause is same-Task serialization, global capacity, or an already-running Desktop turn, show the position within that Task's queue, and allow cancellation. The first status reply is a Card 2.0 message; later phases patch that same message once with a short foreground timeout. If Feishu remains unreachable, the bridge persists the missing queue card or latest patch and retries it in the background without rerunning Codex. Patches for the same message are coalesced to the newest card, and an undelivered queue card is discarded once that queued input has started. A stop callback sets the local cancellation flag and, for Desktop runs, sends `thread-follower-interrupt-turn`. The bridge reports a run as stopped only after local CLI termination or Desktop confirmation.

The bridge reads `account/rateLimits/read` from the local Codex app-server once per minute and writes the normalized account-level limit buckets alongside aggregate health values in private `runtime-status.json`: active consumers, active runs, configured limit, and last Feishu event time. The Mac App combines that file with queue counts from private state and refreshes its visible dashboard every two seconds. No user, Chat, project, or Task identifier is written to the aggregate health file. Feishu's second-level Task usage analysis reads structured Token and event counters from only the local rollouts the requesting user is authorized to see. It ranks Tasks for the local day or current main-quota reset period and explains cached-context, model-call, reasoning, tool, and compaction drivers. Results are cached in process memory for five minutes and are explicitly presented as relative Task diagnostics rather than exact per-Task billing or quota deductions.

After a Desktop turn starts, the bridge follows its state and immediately asks the owner window to load and broadcast the complete history. Another Codex Desktop window may still show a writer-conflict notice while Feishu owns the active turn, but the Task history and live updates remain available as a read-only view.

Desktop state snapshots can expose command, file-change, and permission requests. The bridge creates a separate approval card and forwards only an explicit one-time allow or deny response. It never grants a session-wide or permanent permission from Feishu.

The primary submission path uses Codex Desktop IPC so the new turn appears in the same desktop Task. A definite first `no-client-found` causes one activation through the supported `codex://threads/<Task UUID>` deep link; after a short owner-settle interval the bridge restores the previously frontmost macOS app and retries only through the same IPC path. Activation is attempted at most once per accepted message. A failed activation returns the explicit manual Desktop/CLI/cancel choices, while any request whose submission may already have reached Desktop is never replayed. Local images use `localImage`, audio uses `localAudio`, and ordinary files use a local `mention` plus attachment context. If desktop IPC is unavailable, the bridge prefers the Desktop App's bundled Codex CLI over a PATH installation, passes images with `--image`, and supplies validated temporary file paths in a controlled prompt appendix. It reads the rollout's `session_meta.cli_version` before considering `codex exec resume`; incompatible or unverifiable fallbacks are blocked without clearing the selected Task.

For results, the bridge sends text first and images/files afterward. It recognizes local or remote Markdown image references in the final message and also collects `image_generation_end.saved_path` events written during the current rollout segment. These image events do not contain a turn ID, so the bridge scopes them by the rollout byte offset recorded immediately before starting the only active turn. Supported local files explicitly linked by the final result are returned as attachments; ordinary web links are left unchanged. Local resources are uploaded from their parent directory because lark-cli requires relative paths. A local image or result file that cannot reach Feishu is copied to a private bounded spool, retried with the original idempotency key, and deleted only after confirmed delivery. The defaults are eight images and four result files per turn, with a 50 MB result-file limit.

Task creation, naming, search, and archive use the published Codex app-server JSON-RPC protocol. The bridge still reads the Desktop catalog for the sidebar-facing project and Task list. Pinning is deliberately not implemented because the current app-server schema has no supported pin method; the bridge never writes Codex SQLite or Electron state directly.
